# ResearchNavigator 2.1 Feedback Closure Design

Date: 2026-08-27
Status: DESIGN FOR USER REVIEW
Baseline package: ResearchNavigator 2.0.0-rc1
Baseline backend gate in current environment: `pytest -q` -> 59 passed

## 1. Objective

Close the real-user feedback loop for ResearchNavigator without inflating claims. The iteration must make paper discovery, paper selection, evidence-grade analysis, paper comparison, candidate-gap generation, challenge search, human confirmation, task execution, source verification, PDF workflows, settings/admin, backup/restore, MCP, authentication, and browser E2E traceable end-to-end.

The product remains an evidence-grounded research-direction and paper workspace. It is not a novelty oracle. Candidate gaps remain hypotheses bounded by search scope and evidence.

## 2. Architecture decision

Use a **selection-first evidence workflow** rather than “last search session as implicit corpus”.

Core flow:

`Research direction/project -> explicit paper selection -> evidence-grade per-paper analysis -> comparison matrix -> gap evidence matrix -> explanatory gap agent -> challenge search -> human confirmation -> research plan`

Paper selection may originate from:

- current search results;
- saved/favorited papers;
- manually resolved papers;
- uploaded-paper records where permitted.

The selected paper IDs and project/direction snapshot are explicit inputs to comparison and gap generation. No comparison or gap workflow may silently depend on the most recent search session.

## 3. Search: precise mode vs discovery mode

### 3.1 Query classification

`precise_mode` applies to DOI, arXiv ID, quoted/full title, multi-concept Boolean query, explicit author/venue/dataset query, or otherwise specific query.

`discovery_mode` applies when the normalized query contains only 1-2 broad concept terms and is not a stable identifier or clear full title. Examples: `attention`, `anomaly detection`, `时序异常`.

The classifier is deterministic, versioned, and recorded in the search session.

### 3.2 Configurable result count

The UI exposes result count 10/20/50, defaulting to 50 in discovery mode and 20 in precise mode. Page size is fixed at 10 for the first release of this iteration.

### 3.3 Discovery composition

For a requested Top50 in discovery mode:

- target 10 `classic_candidate` papers;
- target 40 `frontier_candidate` papers.

This is a ranking target, not a guarantee. If evidence fields required by the rule are unavailable, the response records the shortfall instead of manufacturing labels.

`classic_candidate` is an auditable rule label, not an authoritative statement that a paper is universally “classic”. Its rule version is persisted. Candidate eligibility requires high query relevance plus source-verifiable citation/age signals where available.

`frontier_candidate` prioritizes high query relevance and recency, with citation signal used only as a secondary feature.

The ranking implementation must not hard-code famous paper titles such as *Attention Is All You Need*.

### 3.4 Reproducible diversity

Each new discovery search receives a `diversity_seed` generated by the server. The server retrieves a larger high-relevance candidate pool and uses the seed only to rotate papers within relevance bands; weakly relevant papers cannot replace clearly stronger relevant papers merely to create novelty.

- New search with the same broad query: new seed, allowing controlled result rotation.
- Exact session rerun: preserves the original seed.
- External live sources may still change; reproducibility is therefore recorded as query + filters + source set + source status + seed + fetched identifiers + raw response hashes + timestamp, not as a promise of identical future titles.

### 3.5 Search UI state

Search state is stored by search session ID in the URL or navigation state. Opening a paper and returning restores:

- query;
- filters;
- selected sources;
- mode;
- result count;
- page number;
- current result list when the session still exists.

## 4. Explicit paper selection

Replace `RecentCorpusPicker` with a reusable `PaperSelectionPanel`.

Sources:

- `search_session`: choose papers from a selected search session, not implicitly the newest one;
- `favorites`: all favorited papers for the current user;
- `manual`: resolve/add by title, DOI, or arXiv ID if already supported by the paper resolver.

The panel displays titles, year, venue, evidence availability, favorite state, and analysis state. Internal numeric IDs remain implementation details.

Comparison requires >=2 selected papers. Gap generation requires >=1 selected paper plus an explicit project/direction context.

## 5. Evidence-grade paper analysis

Expand structured analysis into evidence-safe fields:

- executive summary;
- research background;
- research problem / task definition;
- theoretical innovation / theoretical contribution, if explicitly evidenced;
- method innovation;
- research route / pipeline;
- input and output;
- core methods;
- new algorithms/modules;
- datasets;
- baselines;
- metrics;
- experimental protocol;
- major results;
- claimed contributions;
- explicit Future Work;
- author-stated limitations;
- system-inferred limitations, visibly separated;
- missing/unknown fields;
- warnings;
- evidence level;
- field-level citations.

Evidence rules remain strict:

- `metadata_only`: metadata facts only.
- `abstract_only`: do not infer full experimental setup, hyperparameters, unmentioned datasets, explicit Future Work, or author limitations.
- full-text evidence levels: may extract only from accessible content and must cite section/page/chunk/source.

Every displayed field has one of: evidenced value, `unknown`, or `insufficient_evidence`. The UI must explicitly display `摘要级证据不足` when appropriate.

The paper page must show the completed analysis after `POST /papers/{id}/analyze`; asynchronous runs, if used, expose job progress and refresh the analysis panel on success.

## 6. Paper comparison matrix

Comparison is no longer metadata-only.

Inputs:

- explicit selected paper IDs;
- explicit project/direction snapshot.

Rows include:

- research problem and task definition;
- input/output;
- prediction horizon where applicable;
- method and method innovation;
- theoretical contribution;
- research route;
- datasets;
- baselines;
- metrics;
- label definition and split protocol where evidenced;
- main results;
- Future Work;
- limitations;
- evidence level;
- missing fields;
- direction relevance score and component explanation.

Each cell carries evidence provenance. Missing evidence is not silently converted to “paper does not do X”.

## 7. Candidate gap engine + explanatory agent

### 7.1 Gap inputs

Gap generation receives:

- project ID;
- selected paper IDs;
- current research profile/project direction snapshot;
- evidence-grade analyses for selected papers.

It never falls back to “latest search results”.

### 7.2 Evidence matrix

The matrix includes, where evidenced:

- paper;
- task;
- input;
- output;
- data type;
- dataset;
- supervision;
- prediction horizon;
- method;
- business/engineering constraints;
- online/offline;
- cross-device/cross-domain;
- imbalance handling;
- false-positive evaluation;
- event-level metrics;
- code/data availability;
- Future Work;
- Limitations;
- evidence level;
- missing fields.

### 7.3 Explanatory Gap Agent

Add a bounded `GapExplanation` node to the existing auditable workflow. It is not an autonomous multi-agent system and does not prove novelty.

For each candidate gap it explains:

- why this candidate was generated;
- which selected papers support the observation;
- which adjacent papers weaken it;
- what evidence is absent;
- what parts are direct evidence vs inference;
- relation to the user's selected direction;
- main novelty-risk factors;
- what challenge queries could overturn it;
- minimum validation experiment;
- why confidence is low/medium/high.

If no LLM provider is configured, a deterministic evidence-template explanation remains available. LLM output must pass citation/evidence validation before storage.

UI uses stage labels such as `matrix -> candidate -> explanation -> challenge -> awaiting_human_confirmation`, never an indefinite spinner.

## 8. Favorites as a first-class research corpus

The library page gains multi-select actions:

- compare selected;
- explore candidate gaps;
- remove favorite;
- manage tag/note/reading status.

Selections transfer as explicit paper IDs to the comparison/gap pages. They remain user-scoped.

## 9. Responsive UI

Desktop:

- fixed/collapsible 264px sider;
- content area uses remaining width;
- wide comparison tables use horizontal scrolling.

Tablet/mobile/narrow window:

- sider collapses to an accessible drawer/menu button;
- header never forces the navigation off-screen;
- search form becomes vertical;
- cards and selection controls use full width;
- tables retain horizontal scrolling instead of shrinking columns into unreadable text.

Add browser tests at multiple viewport sizes. The acceptance condition is that navigation remains reachable at narrow width, not merely that CSS compiles.

## 10. Functional coverage closure

Create a `Page -> API -> table/storage -> acceptance evidence` matrix covering at minimum:

- register/login/logout;
- dashboard;
- research profile;
- projects;
- search/session/rerun;
- paper details;
- evidence-grade analysis;
- favorites/tags/notes/reading status;
- PDF upload/list/parse/retrieve/delete;
- compare;
- candidate gaps;
- challenge search;
- human confirmation;
- plans;
- jobs/events/cancel;
- source status and active source test;
- user settings;
- admin config status/configurable safe settings;
- backup/restore/export;
- MCP tools;
- persistence/restart.

Every row has one of `PASS`, `FAIL`, `BLOCKED`, `SKIPPED`, `NOT_IMPLEMENTED`. `PASS` requires an executed current-checkout acceptance command.

## 11. Live-source acceptance vs deterministic regression

Split validation into two lines.

### 11.1 Deterministic offline regression

Fixture-based tests prove:

- normalization;
- deduplication;
- query classification;
- Top50 composition rules;
- diversity seed determinism;
- pagination;
- selection state;
- analysis evidence boundaries;
- comparison/gap behavior;
- auth/permission/idempotency.

### 11.2 Real-source smoke

Real OpenAlex/arXiv/Crossref/Semantic Scholar smoke tests record:

- query;
- source;
- request timestamp;
- HTTP/status state;
- returned stable identifiers;
- raw response hash or provenance raw hashes;
- count actually returned;
- failure/rate-limit state.

They do not assert fixed titles or fixed counts. A live-source smoke cannot replace deterministic tests.

`SourceRequest` becomes the persisted audit record for actual source calls.

## 12. HTTP-first scenario orchestrator

Acceptance scenarios operate through HTTP APIs after database bootstrap/auth fixture setup.

Direct ORM/DB manipulation is allowed only for:

- creating a clean runtime database;
- deterministic seed fixture insertion where no public API is designed for fixture seeding;
- independent post-run audit queries.

The scenario body must use HTTP for authentication, validation, permissions, state gates, and domain mutations.

## 13. Human confirmation semantics

Any automated harness option such as `--confirm-demo-gap` is renamed/reported as `simulated_human_confirmation`.

Default real scenario:

1. gap reaches `awaiting_human_confirmation`;
2. automation stops;
3. a human confirms through the UI/API with an explicit action;
4. only then may plan generation proceed.

Reports must never label automation-driven confirmation as expert review.

## 14. Browser E2E

At least one Playwright flow starts from login and performs:

1. login;
2. research direction/project selection;
3. paper search;
4. verify result pagination;
5. select papers by title;
6. open a paper, run evidence-grade analysis, verify analysis becomes visible;
7. return to search and verify search/page state restored;
8. favorite papers;
9. compare selected favorites against current direction;
10. generate candidate gap from explicit selections;
11. inspect explanatory agent output;
12. run Challenge Search;
13. verify human confirmation gate;
14. verify sidebar/navigation at a narrow viewport;
15. exercise a meaningful error state.

A separate persistence test may restart the service if the environment supports it.

## 15. Worker acceptance

`pending` is not success evidence.

Worker tests wait for a terminal status:

- `succeeded`;
- `failed`;
- `cancelled` where cancellation is the expected behavior.

They verify:

- event sequence;
- attempt count;
- result/error;
- cancellation semantics;
- retry behavior;
- restart recovery where runnable.

If no worker is running, the acceptance row is `BLOCKED`, not PASS.

## 16. Idempotency

Add scenario-level `scenario_version` and deterministic idempotency keys for create/mutate operations that can be replayed.

Repeated execution must not duplicate:

- user/project;
- favorites;
- tags/paper tags;
- notes intended to be scenario-singletons;
- paper selection sets/comparison runs where the same idempotency key is reused;
- gap candidates;
- plans;
- jobs.

Version behavior:

- same scenario version + same idempotency key -> reuse/update defined resource without duplicate;
- changed scenario version -> create a new run/version when historical comparison matters;
- immutable historical evidence is never silently overwritten.

## 17. Settings and admin

### User settings

Persist safe preferences such as:

- default result count;
- default paper page size (initially constrained to 10 for search results);
- preferred sources;
- default open-access filter;
- display language;
- analysis execution preference where safe.

Secrets are never browser-stored.

### Admin

Provide authenticated admin configuration/status for non-secret operational controls and presence/status of credentials. Raw API keys remain server-side and are never returned to the browser.

Admin acceptance includes 403 for non-admin users.

## 18. Backup/restore and MCP

Expose backup/restore/export capability in the traceability matrix and UI documentation. Destructive restore remains an administrator/offline operation unless a safe authenticated upload flow is explicitly implemented.

MCP acceptance is performed with the official SDK/stdio when the dependency is available. Contract-only tests remain clearly distinct from live stdio acceptance.

## 19. Database/migration plan

Use behavior-bearing additions rather than a broad schema rewrite. The schema changes are fixed as follows:

- extend `search_sessions` with `search_mode`, `ranking_rule_version`, `diversity_seed`, and `composition_json`;
- add `user_settings` with one row per user and safe preference fields/JSON;
- add `paper_sets` and `paper_set_items` to persist explicit selected-paper corpora with user/project scope and purpose;
- add `comparison_runs` to persist project/direction snapshot, selected set, matrix JSON, analysis version, and evidence hash;
- add `gap_explanations` as an append-only versioned explanation record linked to `gap_candidates`;
- add `idempotency_records` keyed by `(user_id, operation, idempotency_key)` with request hash, resource type/id, scenario version, and response snapshot;
- extend `gap_candidates` with `paper_set_id` and `direction_snapshot_json`;
- use the existing `SourceRequest` table for real source request audit instead of creating a duplicate table.

Alembic upgrade and downgrade operations must be explicit. The migration test upgrades an existing pre-change schema to the new head and then exercises the new tables/columns; a fresh `Base.metadata.create_all` is not accepted as migration evidence.

## 20. API plan

Preserve current endpoints where possible and add/extend behavior without unnecessary API churn.

The API additions/extensions are fixed as follows:

- extend `POST /search/papers` request with `mode=auto|precise|discovery`; response adds `search_mode`, `diversity_seed`, `ranking_rule_version`, and per-result ranking metadata;
- preserve `limit` as the size of the persisted search result set; UI accepts 10/20/50 and paginates the persisted set in pages of 10;
- `GET /search/sessions/{id}/papers` returns the persisted session corpus in stored ranking order;
- existing `POST /search/sessions/{id}/rerun` reuses the original diversity seed; a normal new search receives a new seed;
- `POST /paper-sets` and `GET /paper-sets/{id}` persist/retrieve explicit paper selections; `GET /paper-sets` lists the current user's reusable sets;
- extend `GET /library` so favorite items expose complete selection-card paper metadata;
- `POST /comparisons` creates an evidence-aware comparison run from `project_id` + `paper_set_id`; `GET /comparisons/{id}` returns the persisted matrix;
- extend `POST /gaps/generate` to accept `paper_set_id` (and retain `paper_ids` only as a compatibility input that is immediately normalized into a persisted set); direction context is snapshotted from the selected project/profile at generation time;
- gap reads include the latest validated `gap_explanation` and workflow stage;
- `GET /settings/me` and `PUT /settings/me` manage safe user preferences;
- `GET /admin/config-status` remains status-only for secrets, while `GET /admin/runtime-config` and `PUT /admin/runtime-config` manage a whitelist of non-secret operational settings;
- `GET /papers/{paper_id}/documents` lists the current user's accessible uploaded/authorized documents; existing upload/retrieve/delete endpoints remain authoritative for mutations;
- `GET /jobs` lists current-user jobs; existing `GET /jobs/{id}`, `GET /jobs/{id}/events`, and `POST /jobs/{id}/cancel` remain the terminal-state/cancellation contract.

Every new user-scoped endpoint receives a cross-user denial test.

## 21. Testing order

Use RED -> GREEN -> REFACTOR for every behavior change.

Suggested implementation slices:

1. traceability + baseline evidence;
2. search classification/composition/diversity/pagination;
3. explicit paper selection + favorites integration;
4. expanded evidence analysis + paper page rendering;
5. comparison service/UI;
6. gap explanation workflow/UI;
7. responsive shell;
8. PDF/settings/admin/jobs/source-test UI closure;
9. HTTP-first orchestrator + idempotency;
10. deterministic vs live-source suites;
11. Playwright browser flow;
12. migration/backup/MCP/full gates;
13. docs/PRD/claim boundary/release package.

## 22. Final acceptance and claim boundary

No capability is called complete solely because code exists.

Final delivery reports exact current-checkout status for:

- Python tests;
- ruff;
- mypy;
- frontend typecheck/unit/build;
- Playwright;
- migration;
- backup/restore;
- worker terminal-state tests;
- source deterministic tests;
- live-source smoke where network permits;
- MCP stdio where dependency/environment permits;
- Docker cold start/restart where Docker exists.

Environment-blocked gates remain `BLOCKED/NOT_RUN`. The release claim must not be stronger than the executed evidence.
